# Deploying Palius / CHAK — Vercel + Render + Neon

Three pieces, three hosts:

| Piece | Host | Why |
|---|---|---|
| `apps/frontend` — main product UI | **Vercel** | Next.js App Router, edge CDN, preview deploys |
| `apps/admin` — operator dashboard | **Vercel** | Same, separate project so it can be locked down independently |
| `apps/backend` — Go + Gin API | **Render** | Long-running process, Docker, no serverless cold-start on AI calls |
| Database | **Neon** | Serverless Postgres, branches for preview environments |

The backend speaks **both** SQLite and Postgres. It picks Postgres whenever
`DATABASE_URL` is set, so local dev stays zero-config and production is Neon
with no code change.

---

## 1. Neon — database

1. Create a project at [neon.tech](https://neon.tech). Pick the region closest
   to your Render region (`us-west-2` pairs with Render `oregon`).
2. Copy the **pooled** connection string. It looks like:

   ```
   postgresql://USER:PASSWORD@ep-xxx-pooler.us-west-2.aws.neon.tech/neondb?sslmode=require
   ```

   Use the **`-pooler`** host, not the direct one. Render can run several
   instances and Neon's per-branch connection limit is low; the pooler is what
   keeps you from hitting `too many connections` under load.

3. No migration step is needed — the backend creates its schema on boot
   (`CREATE TABLE IF NOT EXISTS`), including the credit ledger and operations
   tables.

> **Preview environments:** Neon branches are cheap and instant. Create a
> `preview` branch and point Render preview deploys at its connection string so
> test traffic never touches production billing data.

---

## 2. Render — backend API

The repo ships a blueprint at `render.yaml`.

1. Push the repo to GitHub.
2. Render Dashboard → **New** → **Blueprint** → select the repo.
3. Render reads `render.yaml` and creates **two** services: `palius-backend`
   and `palius-worker` (the embedded browser — see §2a).
4. Fill in the secrets it prompts for:

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | Neon pooled string | **Required.** Without it the service falls back to ephemeral SQLite and loses all billing data on every deploy. |
| `ALLOWED_ORIGINS` | `https://app.yourdomain.com,https://admin.yourdomain.com` | **Required in production.** Comma-separated. Unset = all origins accepted. |
| `ADMIN_TOKEN` | auto-generated by Render | Guards `/api/v1/admin/*`. Copy it into the admin app's env. |
| `PALIUS_SECRET_KEY` | auto-generated by Render | AES-256-GCM key for every stored credential. **Never rotate casually** — it invalidates every connection already stored. |
| `GEMINI_API_KEY` etc. | your provider keys | At least one, or the app serves deterministic fallback data. |
| `PALIUS_RATE_CARD` | optional path | JSON override for vendor prices — see below. |
| `PLAYWRIGHT_WORKER_PUBLIC_URL` | `https://palius-worker.onrender.com` | The worker's **public** URL. See §2a for why this is separate. |

5. Deploy. Health check is `GET /api/v1/health`.

Your API base URL is then `https://palius-backend.onrender.com/api/v1`.

> **Cold starts:** Render's free tier sleeps after 15 minutes of inactivity and
> takes ~30s to wake. The blueprint specifies `starter` for this reason — AI
> requests already take seconds and a cold start on top is unusable.

## 2a. Render — browser worker (Level 3 connectors)

`palius-worker` is what lets a user connect TikTok, Instagram, X and the rest by
**signing in through an embedded browser**, with no developer app and no API
approval. The blueprint creates it automatically; two things need attention.

**The plan is `standard`, and that is a floor rather than a preference.**
Chromium plus a login context wants ~1GB. A `starter` instance (512MB) will OOM
partway through a login, which is the worst possible time to fail.

**Two URLs, because two different clients talk to it.**

| Variable | Set on | Points at | Why |
|---|---|---|---|
| `PLAYWRIGHT_WORKER_URL` | backend | Render **private** hostname (wired by the blueprint) | The API's own calls. Keeps the worker's private endpoints off the public internet. |
| `PLAYWRIGHT_WORKER_PUBLIC_URL` | backend | `https://palius-worker.onrender.com` | The **user's browser** opens the frame stream directly. It cannot resolve a private hostname. |
| `ALLOWED_ORIGINS` | worker | the Vercel app URLs | Which origins may open that stream socket. Unset = any origin. |

`WORKER_TOKEN` is generated once by Render and shared into the backend as
`PLAYWRIGHT_WORKER_TOKEN` by the blueprint — you do not set it by hand.

If the worker is not deployed, nothing breaks: the connect dialog reports
browser login as unavailable and says why, and blog destinations configured for
browser publishing fall back to an export.

Verify it:

```bash
curl -s https://palius-worker.onrender.com/health
# {"ok":true,"chromium":true,...}   <- chromium:false means it failed to launch

curl -s -H "X-User-Id: user-1" $API/browser/status
# {"running":true,"detail":"Browser worker is live.","encryptionAvailable":true}
```

`encryptionAvailable: false` means `PALIUS_SECRET_KEY` is unset — the server
will refuse to start a login rather than ask someone for a password it cannot
then store safely.

## 3. Vercel — frontend and admin

Create **two** Vercel projects from the same repo.

### Frontend

| Setting | Value |
|---|---|
| Root Directory | `apps/frontend` |
| Framework | Next.js (auto-detected) |
| Build Command | `npm run build` |

Environment variables:

```
NEXT_PUBLIC_PALIUS_API = https://palius-backend.onrender.com/api/v1
GEMINI_API_KEY         = ...   # only if you use the in-app /api routes
```

### Admin

| Setting | Value |
|---|---|
| Root Directory | `apps/admin` |
| Framework | Next.js |

```
NEXT_PUBLIC_PALIUS_API = https://palius-backend.onrender.com/api/v1
PALIUS_ADMIN_TOKEN     = <the ADMIN_TOKEN Render generated>
```

Then add the two resulting Vercel URLs to `ALLOWED_ORIGINS` on Render and
redeploy the backend.

> **Lock the admin app down.** It shows every customer's spend. Put it behind
> Vercel Authentication (Project → Settings → Deployment Protection → Vercel
> Authentication) so only your team can load it, in addition to `ADMIN_TOKEN`
> on the API. `vercel.json` already sets `X-Robots-Tag: noindex`.

## 4. Deploy order

Order matters because each layer needs the one below it:

```
Neon  →  copy DATABASE_URL
  ↓
Render  →  deploy backend + worker, copy the backend URL + ADMIN_TOKEN
  ↓         and the worker's public URL
Vercel  →  deploy frontend + admin with NEXT_PUBLIC_PALIUS_API
  ↓
Render  →  set ALLOWED_ORIGINS (both services) to the Vercel URLs, and
           PLAYWRIGHT_WORKER_PUBLIC_URL on the backend, then redeploy
```

## 5. Verify the deploy

```bash
API=https://palius-backend.onrender.com/api/v1

# 1. Service is up and knows which provider it is using
curl -s $API/health

# 2. Postgres is connected — Render logs should show "database: postgres (neon)"
#    If they show "database: sqlite", DATABASE_URL did not reach the service.

# 3. Pricing loads (proves the rate card and plan maths are live)
curl -s $API/billing/plans | jq '.plans[].plan.name'

# 4. Admin is actually guarded — this must return 401
curl -s -o /dev/null -w '%{http_code}\n' $API/admin/business

# 5. ...and authorised requests work
curl -s -H "Authorization: Bearer $ADMIN_TOKEN" $API/admin/business | jq '.grossMarginPct'
```

## 6. Updating vendor prices without a redeploy

Model prices drift. The rate card in `apps/backend/pricing.go` is a starting
point, and `PALIUS_RATE_CARD` points at a JSON file that overrides any subset
of it:

```json
{
  "videoMarkup": 2.5,
  "models": {
    "veo-3": {
      "provider": "gemini",
      "modality": "video",
      "video": {
        "perSecond": 0.35,
        "audioPerSecond": 0.10,
        "resolutionMult": { "720p": 1.0, "1080p": 1.5, "4k": 3.0 },
        "minBillSeconds": 4
      },
      "verifiedOn": "2026-08"
    }
  }
}
```

Only the models you list are replaced; everything else keeps its built-in
price. The admin dashboard's **Pricing & Rate Card** tab shows the live values
and when each was last verified.

The economics guard tests (`go test ./...`) fail if any change makes an
operation or a plan sell below cost — run them in CI before deploying a rate
change.

## 7. What is NOT deployed by this setup

- **BullMQ / Redis job queue.** Scheduled publishing needs a worker and a Redis
  instance (Render Key Value or Upstash).
- **Object storage** for generated media. Add S3/R2 before shipping video
  generation, or you will be re-fetching from the provider on every view.
